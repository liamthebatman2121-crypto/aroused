# Production readiness audit

> **Current update (2026-10-10):** The dated implementation and verification sections at the end supersede older checklist statements where they conflict. No live provider credentials were added, no media was transmitted, no media was migrated, and runtime remains SQLite.

Audit baseline 2026-10-08; local follow-up verified 2026-10-10. This checklist distinguishes code that is implemented from provider work that is absent or unconfigured. No provider credential, safety verdict, age check, or human moderation decision is simulated. Provider readiness is visible at `/api/health` and in the authenticated admin panel at `/admin` → **System health**.

## Current integration choices

Google, Reddit, X, age-assurance, malware-scanning, known-content matching, content-safety, and image/video-processing providers are not operational. Provider-neutral scanner interfaces and SQLite job-worker mechanics exist, but no scanner is configured or called and no worker process is running. An S3-compatible private object-storage adapter exists, but no real object store is configured. Resend email delivery is implemented but unconfigured. Do not put credentials in client code or commit a real `.env`. Local media and SQLite remain the application runtime.

- **Resend diagnosis:** runtime configuration was checked by loading `.env` into a short-lived Node process and printing only allow-listed provider status fields. `RESEND_API_KEY` / `AROUSED_FROM_EMAIL` are not configured in the current environment, so this project did not send a real verification message and Resend acceptance/rejection for an actual address cannot be observed. `.env` was not printed or modified. The checked names match `.env.example` and production validation. A configured `AROUSED_FROM_EMAIL` must be a sender/domain Resend accepts; this cannot be verified without a real key and provider test.
- **Email verification — IMPLEMENTED LOCALLY.** `auth/resend-mailer.mjs` centralizes Resend delivery for verification and password-reset messages. It enforces a 10-second timeout, rejects non-2xx responses and malformed success payloads, and accepts delivery only when Resend returns a valid message ID. Safe structured logs include only route, normalized provider error code, component, and HTTP status; they omit recipient, message/code/token, response body, API key, and raw exception text. Signup/resend now return a visible failure instead of a success-shaped response when delivery is unconfigured or rejected; no pending code/hash is stored when the verification email is rejected. Duplicate-account signup keeps the same response shape and sends a generic sign-in notice to avoid distinguishing existing addresses from new addresses.
- **Verification protections — TESTED LOCALLY.** Six-digit codes remain HMAC-hashed at rest, expire after ten minutes, are single-use, have bounded attempts and resend limits, and a failed resend does not rotate/overwrite the previously stored code. The verification modal no longer says “We sent” based only on a generic response; it tells the user to enter the code if it arrives. Password-reset request responses remain generic. The login UI now includes a reset-token flow; reset tokens remain hashed, single-use, and time-limited. No verification code, reset token, password, recipient, or fake provider response was written to project logs.
- **Social OAuth — IMPLEMENTED LOCALLY, NOT REAL-PROVIDER VERIFIED.** `auth/oauth-providers.mjs` and `/api/auth/oauth/:provider/{start,callback}` implement authorization-code exchange, callback binding to a short-lived HttpOnly/SameSite=Lax state cookie plus a hashed single-use SQLite transaction (10-minute expiry), PKCE for Google and X, token/profile validation, unique `user_identities` mapping, session creation, and explicit link mode from account settings. No OAuth access or refresh tokens are retained. Signup callbacks require adult confirmation and the current Terms and Guidelines versions; sessions do not bypass upload age-assurance, email, creator declaration, scanning, moderation, or publication gates. The UI buttons and settings linking controls use existing styling and show a provider-unavailable error until configured.
- **Scopes and provider research:** Google requests only `openid email profile`; its server-flow guidance calls for state and recommends nonce when consuming ID tokens. This implementation uses PKCE and Google UserInfo over HTTPS, not an ID token, and only marks the email verified when Google returns `email_verified: true` ([Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)). Reddit requests only `identity`; Reddit's accessible detailed OAuth flow documentation is in its archived official wiki, so the currently registered app flow and platform terms must be checked before activation ([Reddit OAuth2 documentation](https://github.com/reddit-archive/reddit/wiki/oauth2)). X requests only `users.read`, uses PKCE, and requires an exact callback URI; no email or offline refresh scope is requested ([X OAuth 2.0 Authorization Code with PKCE](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code)).
- **Configuration status:** a secret-safe status check of the current `.env` found Resend, Google OAuth, Reddit OAuth, and X OAuth all `NOT_CONFIGURED`. No credentials were added. Provider status reflects configured values only, not a successful external integration. The exact variable names and local callback URLs are documented as empty examples in `.env.example`.
